## 第一名：public-apis/public-apis

### 它是什么

这是一个由社区人工维护的**公共 API 导航目录**，不是一个可以直接部署的后端服务，也不是把所有 API 统一封装起来的软件开发包。

仓库把来自多个领域的公共 API 按类别整理成表格，并标注：

- API 名称与用途；
- 是否需要 API Key 或 OAuth；
- 是否支持 HTTPS；
- 是否支持浏览器跨域访问（CORS）。

目录覆盖动物、艺术与设计、图书、金融、地理编码、政府开放数据、健康、机器学习、电影娱乐、新闻、科学、体育健身、交通和天气等领域。仓库采用 MIT License。

来源：[仓库主页](https://github.com/public-apis/public-apis)、[README 原文](https://github.com/public-apis/public-apis/blob/master/README.md)。

### 它解决什么问题

开发一个新产品或自动化工具时，最早的成本通常不是写调用代码，而是：

1. 找到可用的数据服务；
2. 判断是否免费、是否需要鉴权；
3. 检查 HTTPS、CORS 和文档质量；
4. 比较多个候选 API。

这个仓库的价值是把“API 发现与初筛”集中在一个可搜索、可贡献的清单中。它更接近技术选型索引，而不是生产依赖。

## 具体应用例子

下面是可以直接立项开发的具体应用，而不是笼统的“天气应用”“电影应用”。它们是基于仓库收录 API 设计的产品例子，不是 `public-apis` 官方客户案例。

### 例子 1：马拉松比赛日天气与配速助手

**目标用户：** 即将参加马拉松、半马或越野赛的跑者。  
**具体场景：** 用户输入“2026 上海马拉松”和起跑地址，应用在赛前 7 天每天更新比赛时段的天气风险。

调用链：

1. 使用 [Nominatim](https://nominatim.org/release-docs/latest/api/Overview/) 的 `/search` 把起跑地址转换为经纬度；
2. 把经纬度传给 [Open-Meteo](https://open-meteo.com/en/docs) 的 `/v1/forecast`；
3. 读取比赛时段的温度、体感温度、降水概率、湿度、风速和阵风；
4. 根据用户目标配速生成分段提示。

用户最终看到的结果示例：

> 07:00 起跑：12°C，体感 10°C，降雨概率 65%，东北风 18 km/h。前半程逆风，建议目标配速放慢 5–8 秒/公里；携带一次性雨衣，补给策略按凉爽天气执行。

实现边界：Open-Meteo 的常规预报最长约 16 天，因此它适合临赛提醒，不能提前几个月给出可靠天气结论。

### 例子 2：Strava 跑量与高温影响分析面板

**目标用户：** 希望分析训练质量的跑者或跑团教练。  
**具体场景：** 用户授权 Strava 后，面板自动解释“为什么同一路线本周配速下降”。

调用链：

1. 通过 [Strava API](https://developers.strava.com/docs/reference/) OAuth 读取最近 30 天跑步活动；
2. 提取每次活动的时间、距离、移动时间、海拔和起点坐标；
3. 用 Open-Meteo 历史天气补充当时的气温、湿度和风速；
4. 对比相似距离和路线，输出配速变化与天气条件的相关性。

用户最终看到的结果示例：

> 本周二 10 公里平均配速比过去四次慢 14 秒/公里；当时气温高 7°C、湿度高 18 个百分点。考虑天气后，本次训练表现处于个人正常区间，不建议仅因配速下降追加高强度训练。

这只是训练分析，不应替代医疗建议；Strava 活动位置也属于敏感个人数据，需要最小化保存。

### 例子 3：博物馆“每日一件馆藏”知识卡

**目标用户：** 艺术史爱好者、教师、博物馆旅行者。  
**具体场景：** 用户选择“卡拉瓦乔”“古埃及”或“印象派”，应用每天推送一件真实馆藏及背景资料。

调用链：

1. 调用 [Metropolitan Museum of Art Collection API](https://metmuseum.github.io/) 的 `/public/collection/v1/search` 搜索关键词；
2. 从返回的 `objectIDs` 中选择作品；
3. 调用 `/public/collection/v1/objects/{objectID}` 获取作品名、作者、年代、部门、材质、馆藏页面和图片；
4. 将字段整理成中英双语知识卡，并保留博物馆原始链接。

用户最终看到的结果示例：

> 今日馆藏：作品名、艺术家、创作年代、材质、所属部门、高清图、Met 原始页面；附一段“观看时注意什么”的导览提示。

如果增加生成式 AI 解读，必须把博物馆原始字段与 AI 生成内容分开显示，避免把推测写成馆方结论。

### 例子 4：豆瓣个人观影档案补全工具

**目标用户：** 有多年观影记录、但海报和影片字段不完整的影迷。  
**具体场景：** 用户导入自己的豆瓣观影 CSV，工具自动补齐 4,000 部影片的海报、原名、上映年份、类型和片长。

调用链：

1. 读取用户导出的片名、年份和个人评分；
2. 调用 [TMDb API](https://developer.themoviedb.org/reference/intro/getting-started) 的 `/search/movie` 查找候选影片；
3. 用原名、年份和导演进行二次匹配，低置信度结果交给用户确认；
4. 调用 `/movie/{movie_id}` 补充影片详情；
5. 生成“年度观影量、国家地区、导演、类型、评分分布”个人看板。

用户最终看到的结果示例：

> 2008–2026 年累计观看 4,126 部；意大利电影 187 部；观看最多的导演为 A；个人高分类型集中在 B；仍有 36 条同名影片需要人工确认。

不能直接覆盖原始记录：TMDb 与豆瓣的片名、版本和上映年份可能不同，应保留原数据、匹配置信度和人工修正记录。

### 例子 5：团队外部 API 白名单检查器

**目标用户：** 经常制作自动化工具的开发团队。  
**具体场景：** 开发者在配置文件中写入一个第三方 API 地址，CI 自动判断它是否满足团队准入要求。

实现方式：

1. Fork `public-apis` 清单，增加 `license`、`owner`、`SLA`、`data_region`、`last_verified_at` 和内部负责人字段；
2. CI 读取项目声明的外部 API；
3. 检查是否支持 HTTPS、是否需要密钥、是否已完成隐私与许可证审核；
4. 未进入白名单的 API 阻止部署，并给出替代服务。

用户最终看到的结果示例：

> 构建失败：`example-api.com` 未完成数据驻留地区和商用许可证审核；建议改用已批准的 `approved-api.com`，或提交安全评审。

这时 `public-apis` 只是候选来源，真正的白名单必须由团队自己验证和维护。

## 风险与独立判断

- **Star 暴涨不等于质量突然提升。** `public-apis` 是成熟清单型仓库，本周增长更可能反映传播、推荐或重新曝光，不代表本周发生了同等规模的技术突破。
- **“Public” 不等于“免费、稳定、可商用”。** 每个 API 的费率、许可证、隐私条款和可用性都必须回到服务提供方核实。
- **目录可能过期。** API 会停止维护、更换域名或改变免费额度；README 中的状态只能用于初筛。
- **它不是统一 API 网关。** 调用不同服务仍需分别处理鉴权、数据格式、限流、错误重试和监控。
- **Star 只是关注度信号。** 技术选型还应查看最近提交、Issue、维护者响应、License 和安全策略。

## 下一步建议

项目后续应每天保存一次 Trending 快照，自己计算连续 7 日增量。这样可以减少对 GitHub Trending 候选机制的依赖，并区分“一次性曝光”与“持续增长”。
